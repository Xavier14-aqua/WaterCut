# WaterCut v1.4.3：BGM 播放恢复

2026-11-21。Windows x64 便携补丁，沿用项目 v11 / 总库 v4，无数据库迁移。

## 问题与复现

[云端第 7 次运行](https://github.com/Xavier14-aqua/WaterCut/actions/runs/44905355378) 已通过 134 项测试、打包和前五组原生回归，在 4A 等待 `shared music clock` 时超时。该次旧日志无法区分音频挂起、视频等待和进度冻结，因此增加了音频上下文、视频事件、播放按钮、状态提示、进度与源调度记录。

在 v1.4.2 的真实 Electron 中，于音频解码返回前调用真实 `AudioContext.suspend()`，稳定复现同一等待超时：画面进度 0，输出仍挂起，音乐却被安排启动，随后到达的状态事件把预览暂停。另有三项回归在修复前失败，分别确认加载期间挂起后未恢复、等待 resume 时取消不能及时结束、输出关闭后仍报告时钟运行。这是已复现的状态缺陷，不把它冒充为旧云端日志中未记录的唯一原因。

正常复跑进一步捕获了实际卡死路径：音频上下文为 running，BGM 源数量始终为 0，暂停的视频每帧触发 seeking / seeked / canplay。播放动画在音乐尚未加载完成时，仍对暂停的画面校正 100 ms 偏差；每次定位触发缓冲处理，取消当前 BGM 加载，形成循环。增加暂停视频时间读数偏差的确定性场景后，旧实现重复出现同样的 0 进度和定位风暴，作为修复对照。

## 修复

- 在全部 BGM 读取 / 解码完成后，再确认音频输出恢复为 running，之后才建立共同时间基准和调度音乐。
- 音频恢复和解码等待响应本次播放的取消信号，暂停 / 换序 / 切后台后旧请求不能安排幽灵音源。
- 音频输出关闭或未能恢复时明确结束播放准备；恢复最多等待 5 秒、解码最多等待 10 秒，给出状态提示，避免一直显示播放却不推进。
- 对已关闭的输出不再重复 close；播放中的真实输出中断继续暂停并保留位置，等待用户再次播放。
- 保留原有音量、入出点、淡变、设备 / 后台暂停和离线跳过规则。
- 初始定位只由元数据加载和用户跳转处理。漂移校正仅在共同音频时钟运行、视频也实际播放且未定位 / 缓冲时执行；容许粗剪解码器 250 ms 内的时间偏差，避免微小时间戳舍入触发定位循环。开始播放会清除旧的暂停提示。
- 云端复跑还发现旧主画面测试只等待数据库提交便立即检查界面，改为等待受控下拉框回填后再执行同一断言；没有重试操作或放宽结果。
- 第 10 次独立复跑在旧脚本拖拽验收失败：上一次重排已回填界面，但刷新资源库尚未完成，拖拽柄仍禁用。验收改为等待拖拽柄可操作，并检查 dragstart 确实携带数据，再发送一次 drop；保留原有顺序、分组和内容断言。该次未执行到 BGM，不计入 BGM 验收成功。

## 验证设计

141 项测试和类型检查通过，其中音频传输 9 项、画面同步 3 项。原生回归增加加载中取消、实际输出 running、视频缓冲后再次推进的断言。CI 执行完整 4A、另一个全新 renderer 的正常播放、真实加载期间挂起，以及暂停视频时间偏差场景；故障注入保留原先的同步播放断言，没有延长其 25 秒时限或加失败重试。

成功和失败都保存有界诊断 JSON；CI 始终上传 `WaterCut-playback-diagnostics`。记录仅来自隔离的合成样例，不写用户项目或密钥。
